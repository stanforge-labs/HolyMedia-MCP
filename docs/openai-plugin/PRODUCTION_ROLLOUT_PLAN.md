# Production rollout plan — document only

No step here is authorized by Draft PR #10. The owner must approve production changes separately.

1. **Before deploy:** Confirm the exact current `main`, successful Foundation/Browser E2E/Compose checks, recoverable PostgreSQL backup, existing Web/API image digests, and current OAuth grant counts without exporting tokens. Confirm Nginx forwards `/.well-known/openid-configuration`, `/.well-known/jwks.json`, `/oauth/userinfo`, OAuth endpoints, and `/mcp/public` to API on the canonical host. Verify no route is captured by Next.js or legacy `/mcp`.
2. **Identity migration:** Apply additive migration `0034_openai_oidc_identity` through the normal deployment process after backup. Its nullable columns leave historical grants and users intact. Do not infer `emailVerifiedSource` for old rows. A rollback of application images should leave the additive columns in place; do not drop them while old/new traffic may coexist.
3. **Key material:** Generate an operator-managed RSA key pair of at least 2048 bits outside Git/CI logs. Provide the key JSON through a protected, read-only file mount and `HOLYMEDIA_OIDC_SIGNING_KEYS_FILE`; set `HOLYMEDIA_OIDC_ACTIVE_KID` to its `kid`. Do not put PEM/JSON in Compose environment because Docker administrators can read it through `docker inspect`. A file mount still exposes the key to Docker administrators and to the API container: limit host and container access, encrypt the backup, and document custody. Never place the key in the plugin ZIP. Keep retired public keys in JWKS for at least the one-hour ID-token lifetime; test planned rotation and only then remove old private material.
4. **Coordinated Web/API release:** Deploy the tested Web consent UI and API through the existing GitHub Actions pipeline, without changing Worker or provider WRITE flags. Avoid an interval where the UI requests `openid email` but API signing keys or migration are absent. Keep one known-good image for each changed service. Standard short health and route checks apply; no new release framework or memory guard.
5. **Post-deploy smoke:** Verify HTTPS issuer and protected-resource metadata, OIDC discovery and JWKS; perform one owner-authorized synthetic OAuth Authorization Code + PKCE flow with CIMD or DCR, consent, ID-token signature/audience/nonce, UserInfo, refresh and revoke. Confirm exact public/legacy audience separation, wrong-workspace denial, and 41 READ tools; no advertising WRITE. Check old READ grants still work. Do not use real advertising credentials for reviewer testing.
6. **Rollback:** If Web/API health or auth smoke fails, use the existing image rollback for changed services. Preserve the DB backup and additive migration until compatibility is understood. Revoke/retire a compromised key through a separate incident procedure; a routine image rollback is not a substitute for key revocation. Record actual image digests, migration status and OAuth smoke results.
7. **Portal after production PASS and owner authorization:** Resolve package identity in the existing OpenAI draft, then Validate ZIP, Connect OAuth, Scan Tools, run five positive and three negative reviewer cases, provide a private reviewer video and credentials via the Portal's protected fields, then request a separate owner decision before submission.

## Existing draft identity decision

The old package root `name` is `holymedia-mcp`; PR #10 changes it to `holypilot` while keeping display name HolyPilot. A higher version number does **not** preserve an immutable plugin identity by itself. In Portal, first inspect whether the existing v0.1.0 draft accepts the renamed package as a new version and whether any installation is bound to the old identifier. If the draft rejects it or installed users would lose continuity, either retain `holymedia-mcp` as the technical root name with HolyPilot display metadata for a compatible v0.1.1, or create a separately identified HolyPilot listing with an explicit migration and user reconnect plan. A 0.2.0 version is appropriate only if there is an actual compatibility break; it does not solve identity mismatch alone. Do not create a duplicate draft automatically.
