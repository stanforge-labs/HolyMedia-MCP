## B2.1 release-specific route (not executed)

PR #10's additive migration path `0034_openai_oidc_identity/migration.sql` makes the ordinary `main` push workflow emit `services=[]`; it cannot incidentally deploy Web, API or Worker. Other changes continue using the existing service detector, including ordinary Prisma schema changes. The only path for this OIDC release is the separate `OpenAI OIDC release (one-time)` workflow, manually dispatched on `main` with the exact merged commit SHA. Its `stage` phase builds and pushes the API image on GitHub Actions **without** contacting the VPS; an authorized operator can then pull that exact digest and use its Prisma CLI for migration after backup. Its `deploy` phase has `preflight → api → oidc-gate → web` GitHub job dependencies; no Worker job exists. A failed preflight/API/OIDC job prevents Web. Neither phase may be dispatched until the owner separately approves B3.

The committed `infra/openai-oidc-release-hold.txt` also prevents **later** ordinary Web/API pushes from accidentally releasing this source before B3; Worker-only pushes continue normally. After B3 LIVE PASS, remove the hold in a separate reviewed commit. Normal Web/API/Worker detection then resumes, including for ordinary Prisma changes. This short-lived hold is required because a later push would otherwise build the same unprepared API/Web source even though the original migration merge was skipped.

Before B3, an authorized operator must verify the trusted SSH fingerprint and install the reviewed `scripts/deploy/ssh-entry.sh` and `scripts/deploy/openai-release-readiness.sh` as root-owned executables. The existing forced-command `authorized_keys` entry remains unchanged. Extend only the deploy user's sudoers allowlist for `/usr/local/sbin/holymedia-openai-release-readiness`; verify with `visudo -cf`. Install the reviewed API-only Compose key bind mount and configure only the non-secret file path and active `kid` in `/etc/holymedia-v2/app.env`. No private PEM or base64 key may appear in an environment variable. Until these exact server prerequisites are installed, the new workflow's `openai-preflight` command fails closed.

After separate owner approval and an operator's read-only inventory, run only the workflow's `stage` phase to build/push the exact API image in Actions, record its immutable digest and verify its OCI source label. Preserve the old API/Web immutable images and take a protected PostgreSQL backup. Validate its SHA-256 and restore procedure; use the staged image's Prisma CLI in a separately reviewed one-off operator command to apply additive migration 0034 without replacing the running API, then confirm no failed migrations. The one-off command and connectivity must be reviewed before execution. Provision a root-owned `0700` directory `/etc/holymedia-v2/oidc` with `signing-keys.json` owned by the API runtime UID 1000, mode `0400`. This lets the non-root `node` process read the **read-only** bind mount at `/run/holymedia/oidc/signing-keys.json` while the parent remains inaccessible to non-root host users. Verify the actual candidate image UID before installation and repeat the disposable test if it changes. Root/Docker administrators remain in the secret trust boundary. Protect encrypted backups of the key and retain old public JWKS members until every one-hour ID token signed with them has expired.

Only after these checks and explicit owner approval, write a root-owned `0600` `/etc/holymedia-v2/openai-oidc-release-ready` marker with exactly five lines: `revision=<approved merged main SHA>`, `backup=<absolute protected /var/backups/adforge-mcp/... file>`, `backup_sha256=<checksum>`, `previous_api=<immutable GHCR digest>`, `previous_web=<immutable GHCR digest>`. The read-only preflight verifies marker ownership, exact source SHA, backup checksum, cached rollback images, the applied migration, five healthy services, private-key access settings and read-only Compose mount. An absent or stale marker blocks release. Remove this one-time marker after completion so a later dispatch cannot reuse it. Never source marker contents as shell code.

The API job builds in Actions and deploys its exact digest through the existing single-service rollback script. The dependent OIDC gate verifies the deployed revision, non-root key-file readability, five healthy services, HTTPS health/ready, discovery, public JWKS without private parameters and `/mcp/public` 401. Only then can the Web job build/deploy. A failed OIDC gate leaves Web untouched; an operator must evaluate and, if required, invoke the existing one-time API image rollback under the separately approved B3 procedure. The workflow does not silently retry or force an API rollback after a successful Docker healthcheck whose OIDC validation later failed.

**Compatibility:** Migration 0034 adds nullable columns only. Existing public/legacy OAuth clients, READ grants, refresh token digests and Anthropic connections remain in place; they must be checked with counts and a post-release authorized smoke before declaring LIVE PASS. The old API image can run against the additive schema and ignores the new key mount, but this remains a production rollback preflight item. Never roll the database schema back merely to revert the Web/API image.

3. **Key material:** Generate an operator-managed RSA key pair of at least 2048 bits outside Git/CI logs. Provide the key JSON through a protected, read-only file mount and `HOLYMEDIA_OIDC_SIGNING_KEYS_FILE`; set `HOLYMEDIA_OIDC_ACTIVE_KID` to its `kid`. Do not put PEM/JSON in Compose environment because Docker administrators can read it through `docker inspect`. A file mount still exposes the key to Docker administrators and to the API container: limit host and container access, encrypt the backup, and document custody. Never place the key in the plugin ZIP. 5. **Post-deploy smoke:** Verify HTTPS issuer and protected-resource metadata, OIDC discovery and JWKS; perform one owner-authorized synthetic OAuth Authorization Code + PKCE flow with CIMD or DCR, consent, ID-token signature/audience/nonce, UserInfo, refresh and revoke. 6. **Rollback:** If Web/API health or auth smoke fails, use the existing image rollback for changed services. Preserve the DB backup and additive migration until compatibility is understood. Revoke/retire a compromised key through a separate incident procedure; a routine image rollback is not a substitute for key revocation. Record actual image digests, migration status and OAuth smoke results.
7. **Portal after production PASS and owner authorization:** Resolve package identity in the existing OpenAI draft, then Validate ZIP, Connect OAuth, Scan Tools, run five positive and three negative reviewer cases, provide a private reviewer video and credentials via the Portal's protected fields, then request a separate owner decision before submission.

## Existing draft identity decision

The old package root `name` is `holymedia-mcp`; PR #10 changes it to `holypilot` while keeping display name HolyPilot. A higher version number does **not** preserve an immutable plugin identity by itself. In Portal, first inspect whether the existing v0.1.0 draft accepts the renamed package as a new version and whether any installation is bound to the old identifier. If the draft rejects it or installed users would lose continuity, either retain `holymedia-mcp` as the technical root name with HolyPilot display metadata for a compatible v0.1.1, or create a separately identified HolyPilot listing with an explicit migration and user reconnect plan. A 0.2.0 version is appropriate only if there is an actual compatibility break; it does not solve identity mismatch alone. Do not create a duplicate draft automatically.
