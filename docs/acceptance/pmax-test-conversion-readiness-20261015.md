## What Google API v24 supports — and what it does not prove

Google documents `ConversionActionService.MutateConversionActions` with `validate_only=true`, `partial_failure=false`, a conversion-customer ID and a `create` operation. Validation skips execution; no action ID or successful measurement follows from a PASS. A `ConversionAction` create has a required unique `name` and immutable `type`; category, status, primary-for-goal, counting and value settings express the intended semantics. The API example creates a `WEBPAGE` action independently of a conversion event. Website measurement additionally needs an actual Google tag/event setup. The conversion customer comes from `customer.conversion_tracking_setting.google_ads_conversion_customer`, which may be a manager; this field can be populated even before tracking is enabled. [Google conversion setup](https://developers.google.com/google-ads/api/docs/conversions/getting-started), [v24 ConversionAction](https://developers.google.com/google-ads/api/reference/rpc/v24/ConversionAction), [v24 create operation](https://developers.google.com/google-ads/api/reference/rpc/v24/ConversionActionOperation), [request validation](https://developers.google.com/google-ads/api/docs/best-practices/testing).

`WEBPAGE` + `SUBMIT_LEAD_FORM` would only be truthful if the **independent MCP service** has a real successfully submitted lead form and an approved success-only tracking design. `SIGNUP` is a separate category for a genuine service signup. Neither an agency Tilda lead nor a button click nor the TEST OWNER-only OAuth login is evidence of either event. A conditional draft is: one uniquely named `WEBPAGE` action, category matching a verified first-party MCP event, `ENABLED`, explicitly reviewed `primary_for_goal`, no invented default conversion value or events; send only to the verified TEST conversion customer with `validateOnly:true` and `partialFailure:false`. A real configuration must not be committed until the event/advertiser identity is approved and the separate write workflow exists. This draft intentionally has **no fabricated event name, URL, action ID or Google response**. [v24 conversion categories](https://developers.google.com/google-ads/api/reference/rpc/v24/ConversionActionCategoryEnum.ConversionActionCategory), [Google website action types](https://developers.google.com/google-ads/api/docs/conversions/categories).

TEST accounts can hold configuration but do not serve ads, produce serving/conversion data, or support conversion uploads. Therefore no live traffic/conversion count is required merely to create an action or validate a PAUSED PMax graph; this is a documentation/code inference, **not an actual PMax Google `validate_only` result for this customer**. It would be incorrect to call the conversion tracking VERIFIED solely because an action exists. The code's PMax preflight requires a same-account `ENABLED` action and matching customer goal; it warns, rather than fabricates or rejects, when the preceding 30 days contain no confirmed conversions. A new mock regression fixes this distinction. [Google TEST-account limitations](https://developers.google.com/google-ads/api/docs/best-practices/test-accounts), [PMax sample prerequisite](https://developers.google.com/google-ads/api/samples/add-performance-max-campaign).
