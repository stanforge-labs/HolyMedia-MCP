## Recommended deployment boundary

Use a **separate TEST VPS/IP** for one internet-reachable HTTPS origin, `https://mcp-test.holymedia.kz`, serving ChatGPT and Claude. This avoids a reload of production Nginx and removes current-host RAM/swap contention. A new host/IP is not yet allocated, so the final A-record value and host-specific port/firewall diff remain pending. If the operator insists on the current VPS, the exact alternative DNS record would be `A mcp-test.holymedia.kz -> 77.240.38.131` (TTL 300); it would require an additive vhost plus global Nginx reload and a documented capacity remediation first. It does **not** require editing the production vhost file, but it does share the edge daemon/failure domain. Do not call that alternative isolated from production.

### Proposed DNS/TLS/proxy diff for the separate TEST host

```diff
 DNS zone holymedia.kz:
+mcp-test 300 IN A <allocated TEST-only public IPv4>
 # No AAAA unless TEST IPv6 routing and TLS are separately verified.
 # Existing mcp.holymedia.kz A and other records stay unchanged.

 TEST host only:
+/etc/nginx/sites-available/mcp-test.holymedia.kz
+/etc/nginx/sites-enabled/mcp-test.holymedia.kz -> ../sites-available/mcp-test.holymedia.kz
+/var/www/mcp-test-acme/  # dedicated HTTP-01 webroot
+/etc/letsencrypt/live/mcp-test.holymedia.kz/  # separate ACME lineage
 # No production vhost/certificate/credential/config changes.
```

The proposed Nginx file is [the non-deployed template](../../infra/test-mcp/mcp-test.holymedia.kz.nginx.conf.example). It binds only the new hostname, redirects HTTP except ACME challenges, serves TLS with a separate certificate, proxies only exact private MCP/OAuth/login/consent/approval paths to loopback TEST API `127.0.0.1:4000` and TEST Web `127.0.0.1:3000`, and returns 404 for all other paths. `/mcp/public`, broad `/api`, admin and diagnostic routes are **not** proxied. ACME HTTP-01 requires DNS first and an approved inbound 80/443 policy; the TLS block must be enabled only after certificate issuance. Certificate issuance creates a private key on the TEST host and is **not authorized by this preparation request**. Renewal and failure alerts require an operator-owned procedure.

The TEST API/Web images must be pinned to a tested immutable digest. Build TEST Web with `NEXT_PUBLIC_API_BASE_URL=https://mcp-test.holymedia.kz` and `NEXT_PUBLIC_PUBLIC_BASE_URL=https://mcp-test.holymedia.kz`; API runtime must use `HOLYMEDIA_PUBLIC_BASE_URL=https://mcp-test.holymedia.kz`, `CORS_ORIGINS=https://mcp-test.holymedia.kz`, `NODE_ENV=production` for Secure host-only cookies, and no `COOKIE_DOMAIN` spanning production. Do not copy production `.env`, OAuth client secrets, Google credentials, database contents or encryption keys. The first TEST launch is read-only: Public MCP write flags false; Google provider Stage write gates false; `GOOGLE_ADS_WRITE_ACCOUNT_ALLOWLIST=8590146099`; Public/V2 write account allowlists empty. A controlled TEST-only write gate change for later Q/R/S mutations is a separate approval and does not itself approve any Google commit.

The new host needs its **own** PostgreSQL, Redis, encrypted vault/keyring and operator-managed backup/restore, unless the user separately authorizes a reviewed TEST-only vault migration from the existing acceptance environment.
