## Обнаруженный и исправленный дефект

На split-origin localhost callback `/oauth/google/callback?state=x&code=x` возвращал относительный `Location: /dashboard/connections?...`, то есть браузер попадал на API `:14404/dashboard/connections` (404), вместо Web `:13300`. Исправлено в [`ProviderController`](../../apps/api/src/providers/provider.controller.ts): redirect формируется относительно проверенной `HOLYMEDIA_PUBLIC_BASE_URL`; шесть callback ожиданий для success/error Google/Meta/TikTok обновлены в [тесте](../../apps/api/src/providers/provider.controller.test.ts). Targeted test: 11/11 PASS. Сам OAuth не проводился. Для отдельного Google TEST профиля указан Web origin `127.0.0.1:23300`, API callback `127.0.0.1:24404`.

## Отдельный Google TEST профиль — подготовлен, не активирован

[`infra/local-google-test/docker-compose.yml`](../../infra/local-google-test/docker-compose.yml) — другой Compose project, отдельные API/Web/PG/Redis ports и volumes, loopback-only bindings, TEST-specific DB, callback и Web origin. [Пример env](../../infra/local-google-test/provider.env.example) намеренно содержит непригодные значения без OAuth client; стек с ним не предназначен для provider работы. Все Google/confirmed writes OFF, allowlist пуст, Google Login и signup tag OFF. [Compose guard](../../scripts/non-vps-google-provider-profile-guard.mjs) проверяет это из rendered config в Linux CI, не стартуя контейнеры и не читая credentials. [Пошаговый handoff](../../infra/local-google-test/README.md) отделяет local startup от owner-approved OAuth, READ, `validate_only` и approved mutation.

Для настоящего подключения нужны: отдельное согласие владельца на TEST-only OAuth и секреты в защищённом WSL-файле вне Git; точный Google Cloud Web OAuth client/project с разрешённым `http://127.0.0.1:24404/oauth/google/callback`; OAuth user с доступом к TEST manager/customer `8590146099`; scope `https://www.googleapis.com/auth/adwords`; проверенный `login-customer-id` из account hierarchy. [Google подтверждает localhost redirect](https://developers.google.com/identity/protocols/oauth2/web-server) для Web server flow; [scope и refresh-token flow](https://developers.google.com/google-ads/api/docs/oauth/internals) описаны отдельно. Специальная [страница Google о developer-token sunset](https://developers.google.com/google-ads/api/docs/api-policy/developer-token) говорит о прекращении требования token с 09.09.2026 и переносе access level на Cloud project OAuth client. Перед первым запросом нужно подтвердить фактический project access; старые overview могут отставать. Никакие VPS vault/DB/OAuth материалы не копируются.

## Исполнимый порядок provider-приёмки после отдельного решения владельца

1. Утвердить точный Cloud project/OAuth Web client, доступ user к TEST manager/customer `8590146099`, secure WSL storage и локальный OAuth flow. После отдельного разрешения поднять новый профиль, проверить localhost/сессии/CSRF/approval, пройти browser OAuth и сделать **READ-only** inventory customer, conversion customer/action/goal, campaign, PMax parent, assets, audiences, BRANDS, geo/language IDs и account access. Без eligible ресурса профиль помечается external prerequisite.
2. По отдельному разрешению выполнить provider `validate_only` существующими bounded builders: Stage 0–4, ConversionAction, PMax fixture и шесть edits. Не подменять отрицательные Google ответы фиктивными IDs. Google TEST не обслуживает объявления и не даст conversions/cost/impressions/CPA ([test accounts](https://developers.google.com/google-ads/api/docs/best-practices/test-accounts)); буквальные §§83–85 и 2.06 требуют другого разрешённого реального источника.
3. Только после точного READ/validation и нового immutable preview с BEFORE/AFTER/TTL получить отдельный OWNER browser approval для каждой обратимой mutation. Один commit, provider reread, audit; restore через отдельный preview/approval. Не выполнять destructive delete для повторения прошлых сценариев, не включать PMax автоматически.

**Ручная стоп-точка сейчас:** решение владельца о локальном TEST-only Google OAuth, передаче TEST-only OAuth client credentials безопасным способом вне чата и разрешении будущего READ-only inventory. Пока такого решения нет, новый профиль остаётся не запущен, а текущий disposable стек — без Google credentials.
