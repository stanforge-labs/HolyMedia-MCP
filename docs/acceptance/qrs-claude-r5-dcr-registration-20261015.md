## Controlled public-client contract probe

A single synthetic TEST public DCR request through the external HTTPS origin returned **201**. Its response had an opaque client ID, exact redirect list, authorization-code/refresh grant types, `code` response type, `none` token authentication, declared READ+WRITE capability, numeric `client_id_issued_at`, JSON content type and `no-store`. No authorization, owner consent, code or access/refresh token was requested. The exact diagnostic DB row was then marked **revoked**; a fresh TEST DB query confirmed `status=revoked`, `revoked_at` set and **zero** transactions, codes, access or refresh tokens for that row. The synthetic callback used a reserved non-routable test domain and is not a proposed Claude callback. This proves the endpoint accepts a standard public-client payload; it does **not** prove compatibility with the unknown R5 payload.

## Narrow remediation and evidence boundary

Feature code commit `42b9dbe` adds a TEST-restricted, enumerated `validationReason` to rejection logs without persisting or printing redirect URI, user-agent, query, state or token material. The externally returned 400 remains generic. It also normalizes a malformed/null request body to a 400 instead of a runtime crash and removes raw redirect metadata from successful DCR logs. Unit tests cover safe classes for redirect, grant, response, token-auth, application and scope rejects, no raw-value logging, valid public metadata, registration/PKCE and old READ-grant isolation. Local targeted tests **36/36 PASS**; full Windows tests ran with **1464 API PASS / 22 integration skips**, plus format/lint/typecheck/build/Prisma/secret scan PASS. Exact-code [Linux foundation CI](https://github.com/stanforge-labs/HolyMedia-MCP/actions/runs/38621656910) and [immutable API-image CI](https://github.com/stanforge-labs/HolyMedia-MCP/actions/runs/38621656877) both completed successfully for `42b9dbe`. CI is not a live runtime claim.

The user-referenced Anthropic reports describe **different** stages: [#546](https://github.com/anthropics/claude-ai-mcp/issues/546) includes a 201 registration followed by client failure, while [#724](https://github.com/anthropics/claude-ai-mcp/issues/724) describes failure before any server request. Here four real HolyMedia registrations returned 400. Those reports justify checking ingress instead of trusting the popup, not blaming Claude without the rejected-field evidence.

Do not create R6 blindly. After a **stable** resource-gated TEST-only deployment, retry the **same R5 connection once** if its UI permits and inspect the new category. If a fallback public PKCE client is necessary, use only the real Claude redirect URI shown in the user interface; no callback is inferred from examples. All prior READ grants remain separate. No Google Ads preview, commit, provider call or production/main change was made for this incident.
