# Claude R4 CIMD/DCR compatibility — TEST-only candidate

Status: **code candidate locally tested; not yet deployed or native-client verified**. Claude R/A and S remain OPEN. No Google Ads preview or mutation is authorized by this change.

## Evidence and causal boundary

The R4 user selected **Register automatically (DCR)**, but the 11:00–11:59 UTC TEST Nginx window had no `POST /oauth/register`. At 11:52:01 UTC the authorization request used the existing Claude CIMD client, exact TEST resource and S256, and requested only `adforge:mcp:read`. TEST DB confirms a new explicit OWNER consent/code/token family for READ under that old client, not a new DCR client or WRITE grant. See [the sanitized R4 audit](qrs-claude-write-recheck-20261014.md). The corresponding TEST `list_accounts` was audited; there was no matching production MCP call. The server cannot tell why Claude's UI choice differed from the request it sent.

Two server-side compatibility factors were independently found. TEST authorization-server discovery advertised **both** `client_id_metadata_document_supported: true` and `registration_endpoint`. MCP's client-registration preference makes CIMD a plausible choice over DCR when both are offered; this is a standards-based hypothesis for R4, **not proof of Claude's internal selection logic**. The anonymous challenge for the dedicated `?profile=google_ads_write` URL also asked for READ alone. Under the MCP scope-selection strategy, that challenge can lead a new DCR client to request only READ. Neither server factor permits HolyMedia to alter an existing grant or add an unrequested scope at token issuance.

## Narrow candidate and boundaries

Only when `QRS_TEST_RESTRICTED_AUTH=true`, whose startup validation requires the canonical `https://mcp-test.holymedia.kz` origin and single-account allowlist `8590146099`, authorization-server metadata now omits `client_id_metadata_document_supported`. It still publishes DCR, issuer/resource, S256 and the enabled scope inventory. Existing CIMD registrations and READ grants remain accepted and unchanged; production metadata still advertises CIMD.

Only when the dedicated QRS confirmed-write gate is also enabled and the request is for the private `?profile=google_ads_write` endpoint, an unauthenticated 401 challenge asks for `adforge:mcp:read adforge:mcp:write`. Plain private `/mcp`, Public MCP and production continue to challenge for READ. This is an **OAuth request**, not scope issuance: a new DCR client must be registered, a new PKCE S256 transaction must explicitly request both scopes, the active TEST OWNER must consent, and the token must remain bound to the TEST resource/workspace. Older READ-only registrations/grants cannot be upgraded by refresh. HolyMedia's separate browser approval remains required before every Google commit; generic V2, Public and Stage 2–4 write gates stay OFF.

The actual Claude behavior after discovery changes is unknown until a fresh native connection. Existing connector R4 may cache its client/discovery; its settings cannot be edited in place. **Do not ask for another connector before the exact new image is deployed and the server metadata/challenge have been externally verified.** If Claude again sends a CIMD URL or requests READ despite the new challenge, stop and collect sanitized route/status/client-class/scope/transaction evidence. Do not broaden the old CIMD registration, mutate OAuth rows, or retry blindly.

The fallback “Use your own OAuth client” requires the exact Claude redirect URI supplied by that UI. Do not guess it or pre-register a public client before observing/validating it. A public PKCE client needs no client secret. Existing READ grants must remain separate. If the client still bypasses DCR, send Anthropic support the redacted timeline: UI selected DCR; no TEST `/oauth/register`; authorize used old CIMD; READ-only consent/token; TEST issuer/resource/S256; exact new discovery/challenge status after cutover; connector edition/version and a screenshot without credentials. Ask whether Claude caches CIMD across connector creations and whether it honors the 401 scope challenge. This is a request for client-behavior clarification, not a claim of a Claude defect.
