# VPS storage and memory audit — 2026-10-15

Итог: на существующем диске 40 GiB адресно освобождено **1,373 MiB (1.341 GiB)**; свободное место выросло с 10,696 до 12,069 MiB. Production и TEST остались healthy, защищённые backup/rollback/volumes/audit сохранены. Экономия RAM **не доказана**; крупные оставшиеся образы и журналы без подтверждённой политики хранения не удалялись.

Scope: existing HolyMedia VPS only. The initial inventory was read-only while a separately operated Search Clone acceptance was active. After its preview expired without a commit attempt, narrowly proved disposable cache and TEST images were removed. No deployment, service restart, Google Ads mutation, backup deletion, volume deletion or log vacuum was performed. Measurements span 09:55–10:28 UTC and are not a capacity guarantee.

## Concurrency and safety decision

Before cleanup, the QRS TEST database reported one pending Clone preview. During inventory its browser approval changed from `approved=0` to `approved=1`; deletion was deferred while the approval was live. At 10:19:27 UTC, after the preview's exact expiry, TEST DB counts were `pending=0`, `approved=0`, `inflight=0`. The exact preview remained confirmed but `consumed=false`, `commit_attempted=false`; no commit was sent by this audit. Fresh process/health/resource checks then found no observed `pg_dump`, `pg_restore`, Docker build/pull, migration or active APT task. Only after those gates passed did targeted cleanup begin. The current TEST API and Web, production API/Web/Worker, and both PostgreSQL/Redis pairs remained running and healthy.

One attempted broad `du` inventory of `/var` caused material I/O and memory pressure. Its two scanner processes were stopped; no service or data was changed. Subsequent inventory used bounded metadata and Docker accounting only. Do not repeat a broad recursive scan during acceptance.

- Preserve all running images/containers, current TEST Clone image, previous TEST API rollback image, TEST Web image, production image, linked PostgreSQL/Redis volumes, vault, OAuth state, Google Ads audit/change journal, Compose/environment files, and pre-cutover TEST DB/Redis backup. The protected backup parser had passed in the preceding cutover checkpoint; this audit did not restore or alter it.
- Preserve the three stopped recovery/acceptance containers while the Clone acceptance and its future recovery path remain open. They are small (~82 KB writable layers combined), so deleting them would not materially help disk space.
- Exactly two generated APT cache files were removed: `/var/cache/apt/pkgcache.bin` (70,823,527 bytes) and `/var/cache/apt/srcpkgcache.bin` (70,781,569 bytes). APT daily services were inactive and no package-manager lock holder or active `apt-get`/`dpkg` was found. `/var/cache/apt` fell from 136 MB to 20 KB. No archive, package list, source or dependency of the running application was removed.
- Exactly five obsolete TEST candidate images were removed by full digest, one at a time: `d540d90b35a4` (source `cdfaf947`), `37ed7b1e0502` (source `8868adea`), `518bb108858f` (source `42b9dbea`), and the original TEST API/Web pair `f1c440952286` / `c734f310c664` (source `ceba617f`). They had no container and no reference in the bounded `/opt` application/recovery scan; current TEST API/Web and explicit rollback images use different digests. Root free space rose 16, 16, 16, 637 and 553 MiB respectively. The removed images are no longer available locally; repull from the registry may be possible but was not tested. No other image, volume, network, backup, log or temp file was deleted, and no cleanup job was installed.
- APT archives were already empty; generic `apt-get clean` would have yielded negligible space. Journald vacuuming or other old image removal might save more, but could erase incident/recovery evidence or rollback capability. They require a separate retention decision and fresh dependency check, not an automatic prune. Docker's displayed `reclaimable` amount rose from 2.344 to 3.159 GB after image removals because of shared-layer accounting; it is not a safe-to-delete set.

The expired confirmed Clone preview cannot be reused; any later Clone acceptance needs a fresh JIT preview and separate approval workflow.
2. Build an explicit allowlist of any additional removable image **IDs** after comparing each candidate with running/stopped containers, protected rollback configuration, Compose references and recovery records. Delete only individually proven disposable IDs with `docker image rm <exact-id>`; measure `df -Pm /` after each. Do not prune volumes or all images.
3. If disk remains tight, review journal retention with the incident owner. Preserve the current security/recovery period, export/verify any required evidence first, then use supported journald vacuuming only to an agreed size/date. Do not manually delete active journal files or `btmp`/OAuth/security logs.
4. Keep existing bounded Docker JSON-log rotation. Consider a dedicated non-destructive alert when free root space falls below 10 GiB plus a safety margin; do not automate dangerous Docker prune. Classify protected rollback/evidence versus disposable CI image IDs at image creation time and keep that manifest with the release checkpoint.
5. Observe RAM/PSI/swap I/O under normal full TEST load. If TEST API startup/heap still drives pressure, change only TEST runtime through a separately guarded deployment and measure before/after; disk cleanup alone is not a memory fix.
