## Оценка guard и практическое решение

Абсолютный счётчик `pswpin` не различает чтение давно выгруженной холодной страницы и новое давление от активного вытеснения. Первые 25 страниц здесь пришли без swap-out, OOM, низкой доступной RAM или существенного PSI. Однако итоговый FAIL этого прохода **нельзя объявить ложным**: дополнительная SSH/`journalctl` проверка совпала с kswapd scan и 477 страницами swap-out, которые отдельный двухсекундный наблюдатель увидел около выхода guard. Guard сохраняется без изменений; решение об иной политике потребовало бы отдельного анализа и разрешения владельца. Безопасность будущего cutover должны подтверждать полный 600-секундный интервал, отсутствие активного swap-out и устойчивого reclaim, PSI some/full, OOM, MemAvailable, production latency/health, а также post-start проверка после image delivery.

**Минимальное обратимое исправление процесса:** после остановки TEST и завершения Docker teardown не открывать параллельные SSH-сессии, не запускать `journalctl`, Docker CLI и прочие проверки в течение guard. Единственный detached диагностический сервис записывает trace на защищённый диск; результат читается только после окончания guard. Это не меняет production или пороги и убирает установленную в этом проходе лишнюю нагрузку. Оно не доказывает, что последующие image pull и Web startup пройдут resource guards.

Для публикации потребуется отдельное разрешение владельца на один Web-only release. В нём: свежая проверка отсутствия TEST операций; защищённый rollback; временная остановка только согласованных TEST приложений; полный исходный guard без параллельных проверок; только при PASS доставка точного immutable image с повторной ресурсной проверкой; затем одна Web-only замена, полный post-start guard, восстановление TEST. Любой FAIL — один rollback и STOP. Этот диагностический проход не даёт разрешения и не заменяет эти gates.
