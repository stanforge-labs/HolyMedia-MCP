# Zero-cost TEST VPS optimization and PMax unblock

16 October 2026 (Asia/Qyzylorda). Scope: `codex/qrs-test-auth-recovery`; no production, system, credential, database, or running TEST container changes. This is a candidate and investigation, not a TEST deployment or Google LIVE acceptance.

## 1. Memory pressure and what the measurements prove

The existing 2 GiB host previously failed the unchanged 10-minute resource guard: minimum MemAvailable **765,628 KiB** versus **819,200 KiB**, swap-out **+940 pages**, 32/61 failed samples, PSI full avg10 peak 1.45, OOM delta 0. Production `/health` and `/ready` and the TEST API/Web/PostgreSQL/Redis remained available. This proves intermittent host pressure, not a single culpable service.

The follow-up root-owned, read-only snapshot measured system.slice about **1,508 MB current** with **559 MB swap**, user.slice about **169 MB current** with negligible swap, host slab **176 MB** (113 MB reclaimable), AnonPages **686 MB**, and page tables **26 MB**. TEST API cgroup was **247 MB current / 0 swap** (about 158 MB anon and 83 MB file); TEST Web **112 MB current / 31 MB swap** (70 MB anon); TEST PostgreSQL **37 MB current / 19 MB swap**; Redis **6 MB current / 2 MB swap**. The swap occupancy is predominantly cold history: it is distinct from the positive `pswpout` delta that failed the guard. No OOM or container memory-limit event was seen. `systemctl list-jobs` had no queued job; APT daily work was inactive, while ordinary cron/snapd/docker daemons remained running. A scoped TEST PostgreSQL read found 1 active, 1 idle and 8 internal connections; Redis reported about **1.4 MB used_memory / 2.6 MB RSS**. There is no oversized TEST DB/Redis pool to remove safely.

The missing floor at the worst prior sample is **53,572 KiB (52.3 MiB)**. A one-off saving of that size cannot establish sustained headroom because workloads and production probes are concurrent. No cache clearing, swap cycling, swappiness adjustment, guard change, or required-service shutdown was used.

A full **600-second / 2,355-sample** interval with the low-overhead observer still recorded **+37 pages of active swap-out**, although minimum MemAvailable was **851,604 KiB** (only **31.6 MiB** above the floor), peak PSI full avg10 **0.18**, and OOM delta remained 0. At most four Node healthcheck processes overlapped, including at most two TEST probes, for **135,657 KiB sampled combined PSS**. All 37 swap-out pages occurred during samples with at least one transient cgroup process; that correlation does **not** identify an initiator. A later 35-second check showed zero new swap-out, direct/kswapd scan delta 0 and no OOM, but cannot negate the failed full interval. Afterward all TEST API/Web/DB/Redis and approval routes and production `/health`/`/ready` returned HTTP 200; production ready latency was **0.112 s**, free disk **11,221 MiB** and free swap **1,554,252 KiB**. The old TEST containers remained healthy with zero restarts/OOM.

## 2. Docker healthcheck hypothesis

Source `infra/test-mcp/docker-compose.single-vps.yml` and running `docker inspect` matched exactly before this change: TEST API and Web ran Node `fetch()` healthchecks every 15 seconds, with a 5-second timeout, five retries and 30-second start period. Running production API, Web and Worker use Node checks every 5 seconds; TEST and production PostgreSQL/Redis use `pg_isready` and `redis-cli` every 5 seconds, and all were healthy. The production configuration was only read. Neither `curl` nor `wget` is present in the tested TEST API/Web images; Bash and `timeout` are present.

A single SSH connection ran a one-process, procfs/cgroupfs observer. It queried Docker only at startup, sampled known cgroup `cgroup.procs` and `/proc` without reading environment, logs, credentials or application data. Results:

The 45-second interval saw at most **two simultaneous Node probes**, at most **one TEST Node probe**, and **112,497 KiB** combined sampled PSS at that moment. Docker health history shows TEST Node checks taking roughly **0.55–0.91 seconds**; production checks are more frequent. The 70- and 45-second intervals had zero active swap-out and PSI full avg10 at most 0.01 and 0.00 respectively, but the full 600-second interval did not. Consequently the Node probes are a **measured transient RAM cost**, while their causal contribution to swap-out is **unproven**. There is no evidence to justify changing production checks now.

If later evidence ties production probes to unsafe peaks, a separate owner-reviewed production procedure would first verify endpoint/Redis-check parity in isolated CI, pin an immutable production image, establish rollback and health/latency baselines, and then request a production maintenance approval. No production healthcheck change or production restart is included in this package.

The TEST-only replacement is `infra/test-mcp/http-healthcheck.sh`: one Bash process opens loopback TCP, requests the real `/ready` or `/auth` endpoint, accepts only an HTTP 200 status line, fails closed for redirects/errors/refusal/stall, uses a 4-second read timeout under Docker's unchanged 5-second outer timeout, and keeps the 15-second interval/retries/start period. It contains no secret or external endpoint. It was executed read-only in each existing TEST image against the live route: API **2,552 KiB PSS / 3,212 KiB RSS**, Web **2,528 KiB PSS / 3,188 KiB RSS**, both HTTP 200. These are **post-request samples**, not measured Bash startup peaks. Comparing them with sampled Node peaks suggests roughly **54–65 MiB per transient probe** of potential saving; it is not a claimed reduction in the long-lived API/Web processes or a proven host guard improvement. The images and Compose are changed in source only. A restart/replace is required to observe sustained runtime BEFORE/AFTER; none was performed.

## 3. Observer and diagnostic overhead

The new `scripts/ops/lightweight-health-observer.py` uses one SSH invocation and one Python process, with no Docker calls inside the sampling loop. Its own peak PSS was **9,923 KiB** (70 seconds), **9,718 KiB** (45 seconds), **10,022 KiB** (600 seconds) and **9,491 KiB** (35 seconds). The final 35-second version used **1.464 CPU seconds**. The two short initial windows had zero `pswpout`, whereas the full interval had +37 pages; the observer itself cannot be proved to have caused or prevented them. The first measurement version used Docker inspect JSON locally to resolve PIDs but emitted no environment or credentials; the committed observer requests formatted name/PID only, so protected configuration does not enter its input. The prior +897-page burst coincided with a separate short TEST provider-read startup and multiple cgroup PSI rises; coincidence alone does not establish that read or the older observer as the cause. Avoid repeated Docker CLI/SSH/process-stat scans during guarded deployment. The observer explicitly reports its own PSS and swap deltas; it never masks swap-out.
