## Single-use execution package for a later owner-approved TEST window

The [single-use runner](../../scripts/ops/batch2_no_pull_test_once.py) uses the unchanged phase-aware [maintenance/full guard](../../scripts/ops/batch2_test_maintenance_guard.py) and original floor/rollback policy. It does not invoke `docker pull`. The exact CI artifact is `qrs-test-no-pull-<CI source SHA>` from the successful no-pull workflow run; the artifact ZIP contains `qrs-test-api-delta.tar.gz`. Do not use an image tag or rebuild the delta on the VPS.

After separate owner permission, download the **successful exact-source CI artifact outside the VPS**, extract the tar there, and transfer that tar plus these seven source files into `/opt/holymedia-qrs-test/batch2-no-pull-staging/` (root-only 0700 directory, files 0600):

1. `scripts/ops/batch2_no_pull_test_once.py`
2. `scripts/ops/batch2_test_maintenance_once_v2.py` (helper only; its former pull entrypoint is not called)
3. `scripts/ops/batch2_test_maintenance_guard.py`
4. `scripts/ops/maintenance_guard_policy.py`
5. `scripts/ops/web_only_guard_policy.py`
6. `scripts/ops/no_pull_api_bundle.py`
7. `infra/test-mcp/no-pull-web-health.override.yml` (use this filename in staging)

The runner pins SHA-256 for items 2–7 and the tar and manifest; verify item 1 against the approved Git revision before invocation. Run **once** as root, preserving terminal output and the run directory:

```sh
python3 /opt/holymedia-qrs-test/batch2-no-pull-staging/batch2_no_pull_test_once.py prepare /opt/holymedia-qrs-test/batch2-no-pull-staging/qrs-test-api-delta.tar.gz
python3 /opt/holymedia-qrs-test/batch2-no-pull-staging/batch2_no_pull_test_once.py execute
```

`prepare` checks exact installed images, protected Compose/env, 9 healthy containers, production ready/latency, absence of active TEST previews/approvals/commits/OAuth transactions/long DB transactions, disk/swap/PSI/OOM and background maintenance. It copies the existing rollback configuration and its own exact runner into the protected run directory, makes fresh TEST PostgreSQL/Redis backups and verifies their headers, SHA and `pg_restore -l`. It checks the tar and each code file, constructs read-only mounts, and compares the complete Compose model so only `qrs_web.healthcheck` and `qrs_api.volumes` differ. No production service is stopped or changed. A failed `prepare` blocks execution.

`execute` verifies all prepared hashes again, then stops **only** TEST Web followed by TEST API. It confirms TEST DB/Redis and production still run, executes the complete 600-second maintenance-state guard, and starts exactly one TEST API and then one TEST Web from the **already installed old images** with `--no-build --pull never`. It verifies container image IDs, health, all 36 read-only mount hashes, the actual Web healthcheck, TEST-only gates OFF for ConversionAction/PMax/generic writes, auth and approval routes, OAuth metadata/CSRF, protected MCP 401, production identity, and a complete 600-second full-stack guard with strict zero new swap-out. The run directory records events, traces, backups and result on disk. If a step after stop fails, it performs **one** original-image/config rollback and stops; there is no automatic second attempt. The previous as-run rollback directories and backups remain untouched.

**Decision before deployment:** No-pull removes the known pull-time pressure source, but startup/page faults may still fail the unchanged guard. A TEST deployment can be called PASS only after the new full stack passes its entire post-start interval. This package is ready for **one guarded attempt**, not a claim that Batch 2 or PMax LIVE already passed. New Google Ads commits and activation of ConversionAction/PMax gates are outside this authorization and require separate approval.
