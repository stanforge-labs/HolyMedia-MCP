## Стоп-точки и порядок завершения

1. **Защищённый перенос данных — выполнен.** Владелец разрешил перенос несмотря на отсутствие BitLocker. TEST-only архив проверен по SHA, исходная серверная копия и local-before-import backup сохранены. Production credentials/DB не переносились.
2. **Локальная приёмка — частично выполнена.** Restore, связи, vault decrypt, health, маршруты, закрытая регистрация, CSRF получение, anonymous permission boundary и stop → start PASS. Интерактивный OWNER login, consent, реальный browser approval и restore с активной сессией пока **не проверены**: локальные Google callback ещё не зарегистрированы, а владелец не подтвердил password login. Два отдельных callback: provider `http://127.0.0.1:24404/oauth/google/callback`, Google Login `http://127.0.0.1:24404/auth/google/callback`. Клиентские Google разрешения и реальные Ads READ требуют отдельного решения. Не считать HTTP 200 на странице `/mcp/approve` доказательством approval.
3. **Синхронизация перед остановкой — ожидает полной приёмки и отдельного разрешения.** Пока VPS TEST продолжает работать, копия 11:20Z является snapshot, не постоянной синхронизацией. Перед любой остановкой повторно проверить отсутствие pending approvals/commits/OAuth, сделать финальную согласованную копию и сверить counts/хэши. Только после authenticated LOCAL PASS запросить отдельное разрешение на точную остановку четырёх TEST контейнеров. Production и общие зависимости не останавливать.
4. **VPS разгрузка.** После approval остановить только указанные TEST API/Web и их отдельные PostgreSQL/Redis; выставить им restart policy `no` (только этим четырём) для предотвращения автозапуска при reboot. Не удалять контейнеры, volumes, images, backups или audit. Сохранить обратимый `docker start`/restore procedure. Измерить до/после RAM, swap I/O, PSI, CPU, disk и production health/OAuth/MCP. Проверить полный неизменённый resource guard перед любым новым Web release. Новый production cutover потребует отдельного разрешения.

## Внешний HTTPS и границы доказательства

Локальный `127.0.0.1` достаточен для разработки и mock E2E. Для Google Ads Web OAuth нужен утверждённый callback `http://127.0.0.1:24404/oauth/google/callback`; для Google Login существующего OWNER — отдельный `http://127.0.0.1:24404/auth/google/callback`. До регистрации точных URI и отдельного решения владельца Google READ/LIVE остаётся остановлен. Для Claude remote MCP и прежнего публичного TEST origin возможен временный reverse SSH только с ПК к существующему VPS Nginx на его loopback upstream после остановки старых TEST API/Web. Тогда VPS останется HTTPS ingress, а compute/DB/Redis будут локальными; это **не полная независимость от VPS**, требует отдельного разрешения, согласованной HTTPS/OAuth конфигурации и постоянной доступности защищённого ПК. Никакой tunnel, DNS или redirect URI в этой контрольной точке не изменён.

**Текущий итог:** TEST-данные и TEST-only ключи перенесены и локальный стек работает с действующим snapshot. VPS TEST всё ещё работает, все его контейнеры/volumes/backups сохранены; поэтому освобождение RAM на VPS пока **0 МиБ**. Для полного функционального переноса нужен интерактивный OWNER login (при необходимости — регистрация локального Google Login callback), затем отдельное подтверждение на остановку четырёх remote TEST контейнеров. Production Web/API/Worker/DB, Nginx, OAuth, Google Ads Write, main и resource guards не менялись. Сам HolyPilot branding production cutover в этом задании не выполнялся.
