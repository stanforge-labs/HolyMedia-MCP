# Batch 2 — один TEST-only maintenance window на существующем VPS

**Решение на 17.10.2026: CONDITIONAL.** Это готовый порядок одной будущей попытки, а не разрешение на неё. В этой работе VPS не опрашивался, контейнеры и файлы сервера не менялись, образы не загружались. Исходные данные — [Batch 2 read-only preflight](BATCH2_READONLY_RESOURCE_PREFLIGHT_20261017.md), [Batch 1 exact-source package](../acceptance/BATCH1_OFFLINE_EXECUTION_PACKAGE_20261017.md), [TEST Web policy](TEST_WEB_ONLY_RESOURCE_GUARD_POLICY.md) и [ранее выполненная адресная очистка](VPS_STORAGE_MEMORY_CLEANUP_20261015.md). Числа далее исторические, а не обещание текущего состояния сервера.

## Почему именно это окно

На последнем полном снимке `MemAvailable` 817 276 KiB = **798,1 MiB**, на 1,9 MiB ниже действующего пола 800 MiB; в отдельные 30 секунд были `pswpout +21`, `pswpin +20`, `pgmajfault +22`. Повторять полный guard с неизменённым стеком в поиске случайного нуля нецелесообразно. Остановить только TEST API/Web — конкретное изменение нагрузки, которое можно проверить причинно: при исторических cgroup `~199,5 + ~130,5 = ~330 MiB` освобождаемая доля **неизвестна** (cgroup включает cache/shared pages), а старые process PSS `~170–171 + ~83–85 = ~253–256 MiB` тоже не равны гарантированному приросту `MemAvailable`. Нельзя обещать `798+330=1128 MiB`; это лишь оптимистический ориентир. Старый Web Node healthcheck достигал `~59,1 MiB` PSS, Bash probe `~2,5 MiB`: ожидаемое уменьшение **краткого пика** `~56,6 MiB`, постоянной памяти — не измерено.

Production API/Web/Worker/PostgreSQL/Redis и Nginx остаются запущены без изменения образов, конфигураций и маршрутов. TEST PostgreSQL/Redis остаются запущены с прежними отдельными volumes. Во время окна TEST `/auth`, consent, approval, OAuth и `/mcp` будут недоступны; окно допустимо только с объявленным владельцем отсутствием TEST-клиентских операций. Никаких Google writes в рамках этого окна.

## Ресурсный бюджет и стоп-формула

Последний `df` дал **11 881 MiB** свободно, запас над неизменным порогом 10 240 MiB — **1 641 MiB**. API candidate `sha256:68d718998795dd6a0d6229fda0d747c0cb503dbd625d772542b1edacaf48a76f` занял на CI runner дополнительно **775,1 MiB** при сохранённом baseline. Web candidate `sha256:3e8b44908bc9f6752ea996aa699da49b91a85953a98f5c41638811719c888669` имеет **214,3 MiB compressed layers**; его *incremental Docker disk footprint на этом VPS и временный максимум unpack неизвестны*. Web-only production brand image (592,6 MB uncompressed) не подменяет измерение TEST Web candidate.

|---|---|---|

| После старта нового API, затем Web | startup peak неизвестен; API cgroup был `~199,5 MiB`, Web `~130,5 MiB`; нельзя вычитать их из свободной RAM линейно | оба старых image/config остаются для rollback, free disk не ниже пола |
| После полного восстановления | возможная экономия только Web probe `~56,6 MiB` transient; отсутствие swapping **не доказано** | floor и место для аварийных записей сохраняются; не удалять старые образы ради формального PASS |

Даже нижняя известная цена `API 775 + Web compressed 214 ≈989 MiB` оставляет только **~652 MiB** над disk floor **до** Web unpack, backup и temp. Например, при *иллюстративных*, не измеренных `W=600`, `B=64`, `T=512 MiB` понадобится `10 240+775+600+64+512=12 191 MiB` свободно **перед** pull — на 310 MiB больше последнего снимка. Поэтому нельзя запускать pull на основании одних 11 881 MiB. Перед будущим окном получить проверенную верхнюю оценку `W` и `T` из одноразового disposable CI/local Docker pull или manifest/layer accounting; на VPS сверить фактический `df` на каждой фазе. Если прогноз с резервом и rollback не помещается, допускается **только отдельная адресная** очистка подтверждённо disposable TEST cache/image IDs после проверки всех running/stopped references, Compose, rollback и audit. Последняя очистка уже сняла очевидный BuildKit/APT cache; `docker prune`, volumes, journal/security logs, protected/unknown images и backup не трогать. Если безопасной очистки нет — **STOP до остановки TEST**.

## Одно исполнимое окно: последовательность и границы

Нужна новая явная санкция владельца на **обе отдельно названные TEST Web и TEST API замены**, временную остановку обоих TEST приложений и иной порядок preflight: один 600-секундный интервал **после снятия TEST нагрузки**, вместо повторного full-stack preflight неизменённого старого состояния. Численные RAM/swap/PSI/disk/OOM/latency guards не меняются. Этот maintenance-state guard **не является full-stack PASS**; единственный финальный PASS возможен лишь после восстановления обоих приложений. Отдельно согласовать точные disposable IDs, если выяснится необходимость дисковой очистки. Ранее выданное Web-only разрешение не распространяется на API и не разрешает изменение порядка.

1. **Перед любой остановкой.** Сверить CI source/digest/labels: Web `6b212d4bdebd1dcfc191de27a03ad4963c09b7d3` и указанный выше digest; API `e5216c8f66a5e6b9c8afd1290b221accff069f41` и указанный выше digest. Локально/CI измерить combined pull/unpack disk peak с сохранением baseline images. На VPS только лёгкий одномоментный gate: `MemAvailable`, `SwapFree`, `df`, PSI some/full, `pswpin/pswpout`, major faults, OOM, Docker health/image/restart, production `/health` и `/ready` latency, TEST API/Web/DB/Redis, отсутствие APT/Docker pull/build/migration/backup. Production failure, OOM, высокий PSI или недостаточный прогноз диска → STOP. Пограничный RAM full-stack снимок сам по себе не запускает image pull; именно остановка TEST должна доказать освобождение.
2. **Защита восстановления.** Сначала объявить TEST-паузу владельцу и удостовериться в отсутствии активных клиентских операций; затем до остановки сохранить root-only (0700 каталог/0600 файлы) точные старые Web/API image IDs, текущие Compose/override/env *файлы как protected копии без вывода значений*, checksums, TEST DB `pg_dump -Fc`, TEST Redis RDB, `pg_restore -l`, header/hash/размер, volume names, Docker container config и проверенные команды возврата. Backup создаётся в TEST protected storage после расчёта `B`; не копировать vault/DB/OAuth в публичный CI. Ни production DB, ни TEST volumes не заменять. Кандидат не содержит миграции; при обычном rollback **не** перезаписывать TEST DB/Redis, чтобы не стереть появившиеся транзакции. Старые образы сохранить локально на всём протяжении окна.
3. **Дренировать TEST.** Владелец закрывает активные ChatGPT/Claude TEST-сеансы и не начинает новые до конца окна. В TEST DB (без вывода токенов) дважды проверить `mcp_previews`: pending/unexpired, approved/unconsumed, `commit_attempted_at IS NOT NULL AND commit_status IS NULL` — строго `0/0/0`; отдельно не должно быть живых `oauth_authorization_transactions` (`expires_at>now() AND consumed_at IS NULL`) и неиспользованных действительных OAuth codes. Проверить отсутствие активной транзакции write/долгой provider операции, миграции и DB backup. Если что-то есть — дождаться нормального завершения/expiry либо отменить окно, **не** сбрасывать запись. Между проверкой и остановкой возможна гонка: сначала остановить TEST Web (не позволяет новый browser approval), затем TEST API с достаточным grace timeout и `enableShutdownHooks`, проверить оба stopped/`AutoRemove=false`, затем **повторно** прочитать counts/commit status. Если появился неопределённый commit — не заменять image, выполнить только provider READ reconciliation в отдельном разрешённом процессе и восстановить старый TEST. TEST ingress будет отдавать ошибку во время окна; production origin не меняется. Внешний MCP клиент теоретически может попасть в API до stop, поэтому повторная проверка после stop обязательна, а нулевой риск гонки без отдельного TEST ingress drain не заявлен.
4. **Проверить результат снятия нагрузки.** С остановленными только TEST Web/API и работающими TEST DB/Redis и всей production выполнить **один** 600-секундный maintenance-state интервал с одним lightweight observer/SSH: `MemAvailable ≥819 200 KiB`, `SwapFree ≥262 144 KiB`, `disk ≥10 240 MiB`, PSI full `<1.5`, OOM delta 0, **strict `pswpout delta=0` для будущего API**, production health/ready 200 и ready `<0.8 s`; PSI some/swap-in/major faults также сохранить и отклонить явно серьёзный sustained pressure. TEST auth/approval намеренно недоступны и не засчитываются как PASS. Существующие full-stack observers ожидают запущенные TEST API/Web, поэтому для этой фазы нужен предварительно локально проверенный state-aware режим того же лёгкого наблюдателя; запускать их неизменёнными с подавлением ошибок TEST нельзя. Если интервал FAIL — один возврат старых Web/API, STOP, без повторного ожидания нового окна. Этот замер проверяет конкретную гипотезу `TEST нагрузка → pressure`; не доказывает capacity полного стека.
5. **Загрузка без параллельных экземпляров.** Только после шага 4 по одному загрузить pinned Web и API digest; удобный порядок pull выбирается по фактическому дисковому бюджету, старые image IDs никогда не удаляются. Во время каждого pull/unpack контролировать численные floors, PSI, OOM, production latency и строгий `pswpout=0` относительно начала фазы; замерить peak disk, а не только `df` после pull. Если нет достаточного места для **обоих** candidates, backup, временных файлов и старых rollback images — не делать первый pull. Любая ошибка → восстановить старые TEST контейнеры и STOP; не повторять pull автоматически.
6. **Единственные новые экземпляры.** Сохранить исходные TEST origin, loopback ports, networks, OAuth/env, owner/customer allowlist и production flags. Поднять **один** новый API через pinned image, `--no-deps --no-build --pull never`, проверить image identity, `/health`, `/ready`, PostgreSQL/Redis, 401 для неавторизованного MCP, flags default-OFF, отсутствие рестартов/OOM; затем **один** новый Web и его реальный Bash `/auth` healthcheck. Не запускать old/new API или Web параллельно. Проверить TEST login, consent, CSRF, `/auth`, `/mcp/approve`, API connectivity, OAuth metadata, английские маршруты; не создавать preview/commit/Google mutation. Во время startup — короткий частый fail-fast контроль тех же floors, swap/PSI/OOM/production latency; нельзя объявлять короткий smoke 600-секундным PASS.
7. **Единый финальный полный guard.** После прогрева и восстановления всех **девяти** containers провести **один** законченный 600-секундный trace. Требования: исходный API strict no-new-`pswpout` (`0`), TEST Web-only дополнительные PSI some/swap-in/major-fault/rolling caps, `MemAvailable ≥819 200 KiB`, `SwapFree ≥262 144 KiB`, `disk ≥10 240 MiB`, PSI full `<1.5`, no new OOM/restart, все TEST/production HTTP и approval routes 200, production ready `<0.8 s` (и `<0.5 s` при page-out согласно Web policy), approvals/commit снова `0/0/0`. Один trace можно оценить двумя существующими профилями, но API Web-послабление swap-out **не получает**. Недостающие samples/обрыв наблюдателя = FAIL. Только здесь возможен `BATCH 2 PASS`; наблюдение TEST off не заменяет его.
8. **Единый rollback без повтора.** При любом fail-fast нарушении или финальном FAIL остановить новые TEST Web/API (если они стартовали), поднять старый API и старый Web **по одному** из сохранённых image/config без pull, проверить image IDs, TEST DB/Redis, OAuth/approval, production health/ready и resource floors. Если восстановление старого полного стека само активирует swapping, зафиксировать `ROLLED BACK / resource BLOCKED`; не держать TEST Web выключенным как постоянный «успех» и не объявлять безопасность production без измерений. Если возвращение полного стека создаёт острое давление, оставить лишь временную TEST-only maintenance паузу для защиты production **как инцидент**, уведомить владельца и не делать второй cutover. DB/Redis restore — только при доказанном повреждении, с отдельным решением по свежим транзакциям.

**Безопасность rollback:** это замена только контейнеров TEST API/Web и защищённого TEST Compose override; immutable old images не удаляются, secrets не покидают VPS, production compose/images/DB/OAuth/Nginx не меняются. Проверить `docker compose config` с защищёнными файлами без печати secret values, точное соответствие container labels и root-only права. Любая неожиданная drift source/digest/config либо `AutoRemove=true` до stop — STOP без мутации.

## Если полный стек снова меняет swap

Это означает **FAIL конкретной попытки**, даже если maintenance-state guard был PASS и Web probe стал легче. Провести один rollback и зафиксировать trace `before stop → TEST off → pull/start → full-stack`, не повторяя окна. Сравнить фактические cgroup anon/file, PSS startup/steady, host reclaim, PSI, `pswpout` и `pgmajfault`; записать конкретный новый TEST-only bottleneck. Дальнейшее исправление — отдельный offline source-level patch и CI, если trace действительно выявит сократимый модуль/пул/healthcheck; без доказательства не ставить произвольный Node heap limit. Старые production healthchecks, Docker daemon/system settings и protected volumes не менять. Если полный стек после уже измеренной Web-экономии снова не проходит, на текущем VPS Batch 2 не закрыт; ранний pass при выключенном Web/API не меняет вывод.

## Бесплатный fallback для Google LIVE

Существующий GitHub Actions уже пригоден для mock/integration/security/image smoke и измерения диска disposable образов **без** TEST vault, OAuth tokens или protected DB. Это **не** Google LIVE и не browser approval. ПК владельца может стать локальным TEST host только при отдельно доказанных свободных RAM/диске, закрытом доступе и шифровании, изолированной DB/Redis, корректном HTTPS public origin/Google OAuth redirect, ручном owner login/approval и отдельном безопасном переносе credentials; сейчас такой стенд не подтверждён и его нельзя объявить готовой заменой VPS. Простые локальные Google `validate_only` с новым owner grant могли бы подтвердить provider schema, но не full TEST MCP preview/commit/approval/reread. Реальные Google writes, TEST ConversionAction/PMax и prod release остаются отдельными разрешениями после Batch 2.

## Разрешения и конечное решение

1. **Сейчас нужны два раздельно сформулированных разрешения в одном решении владельца:** на TEST Web replacement и на TEST API replacement в рамках одного TEST-only maintenance window, плюс согласие на TEST downtime и maintenance-state preflight вместо прежнего неизменённого full-stack preflight. Одно разрешение не подразумевает другое. Это не разрешение на Google commits, gate activation, production или main. Если понадобится адресная очистка диска, её exact ID/diff предъявить отдельно до удаления.
2. После runtime PASS — **отдельное** разрешение на каждую защищённую TEST ConversionAction/PMax gate activation/restart; один image уже содержит оба, но profiles взаимоисключающие и каждый требует своего ресурcного контроля. Затем для каждой реальной Google mutation — отдельные JIT preview, browser OWNER approval и явное owner разрешение.

**Вердикт:** безопасно выполнить Batch 2 на старом VPS без доплат **CONDITIONAL**, но не `YES` по историческим данным. Решение проверяемо за **одну** разрешённую интервенцию с немедленным rollback; заранее доказанный безрисковый full-stack headroom или disk peak отсутствует. Следующий шаг — именно выполнение описанного окна после разрешения, а не очередной full-stack baseline в ожидании случайного PASS.
