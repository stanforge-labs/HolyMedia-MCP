# HolyPilot: прицельная диагностика swap-in перед Web-only релизом

Дата: 2026-10-19. Область: только чтение VPS и сохранённых результатов. TEST, production, образы, настройки и resource guard не менялись.

## Что достоверно известно о заблокированной попытке

- После остановки TEST API/Web `MemAvailable` вырос на 272 164 KiB (265,8 MiB). Guard запущен в 05:06:26 UTC и завершился FAIL в 05:09:11 UTC, через 165,1 с.
- Непосредственный критерий FAIL: `pswpin` +76 страниц при лимите 64 за интервал; пик за 60 с — 72 при лимите 32. `pgmajfault` +70, пик 66. `pswpout` 0; минимум `MemAvailable` 1 109 136 KiB; PSI full 0; OOM 0.
- В сохранённой директории `/var/backups/adforge-mcp/holypilot-brand-only-20261019T050419Z` есть backup конфигураций и Docker inspect, но нет временного ряда per-process/per-cgroup для интервала guard. Сохранённый `resource-guard.py` снимает общесистемные `pswpin`, `pswpout` и `pgmajfault` раз в секунду, а каждые 30 с делает Docker inspect и HTTP health. Его итог содержит агрегаты, а не источник page-in.
- Журнал 05:06:26–05:09:11 UTC показывает вторую SSH-сессию и чтение release script около 05:06:52–05:06:53, а также запущенный guard. Запусков APT в просмотренном интервале не найдено. Журнал не сообщает, какой процесс поднял страницы из swap. Временное совпадение с SSH, Docker health probes или фоновыми процессами не доказывает причинность.

## Новая лёгкая read-only проверка

Одна SSH-сессия запустила Python-наблюдатель из stdin без записи файлов на VPS. Он каждые 3 с читал `/proc/vmstat`, `/proc/meminfo`, `/proc/pressure/memory`, счётчики `memory.stat` и `memory.swap.current` для `system.slice`/`user.slice`; длительность 36 с при всех девяти работающих контейнерах. Docker CLI, HTTP requests и образы в этом интервале не запускались.

| Показатель | Изменение за 36 с |
| --- | ---: |
| host `pswpin` | +9 страниц |
| host `pswpout` | +144 страницы |
| host `pgmajfault` | +32 |
| OOM | 0 |
| PSI full `total` | +43 005 мкс |
| `system.slice` `pgmajfault` | +32 |
| `user.slice` `pgmajfault` | 0 |
| `system.slice` `memory.swap.current` | +573 440 байт |
| `user.slice` `memory.swap.current` | +8 192 байт |

`MemAvailable` в наблюдаемых точках оставался около 925–961 MiB. Текущие держатели выгруженных страниц включают долгоживущие контейнерные процессы, `dockerd`, `containerd` и системные службы. `VmSwap` и `memory.swap.current` показывают **занятость** swap, а не виновника конкретного чтения страниц. Краткая проверка показывает, что при полном стеке есть реальное фоновое swap I/O и что сам лёгкий наблюдатель не дал major faults в `user.slice` за эти 36 с. Она не воспроизводит конфигурацию с остановленными TEST API/Web и не определяет источник исторических +76 страниц.

## Вывод и следующий безопасный шаг

**Причина прежнего swap-in: INCONCLUSIVE.** Отсутствие swap-out, высокого PSI и недостатка доступной RAM в том guard согласуется с чтением ранее выгруженных страниц, но не доказывает ни конкретный процесс, ни безопасность будущего запуска Web. Сегодня при полном стеке одновременно возникли swap-in и swap-out; считать сервер устойчиво свободным нельзя. Необходимо сохранить исходный 600-секундный guard и все пороги. Повторять Web cutover сейчас технически необоснованно.

Два бесплатных варианта, без изменений production в рамках этой диагностики:

1. **Установить источник до следующей попытки.** В отдельном согласованном окне вести один лёгкий per-cgroup/per-process временной ряд параллельно исходному guard, включая `system.slice` leaf cgroups, `user.slice` и host `pswpin/pswpout/pgmajfault`; исключить параллельные SSH/Docker опросы. При повторном событии сопоставить дельты по тем же секундам. После конкретной атрибуции предложить только обратимое TEST-only устранение и проверить его тем же guard. Если события не будет или источник остаётся неясен — deployment не начинать.
2. **Тихое TEST-only maintenance window после доказанной атрибуции.** Если виновником окажется необязательная TEST-нагрузка или параллельные диагностические задачи, временно остановить только согласованные TEST-приложения; не менять production и системные настройки. Проверить отсутствие операций, backup/rollback, ресурсный guard до и после доставки image, затем один Web-only cutover с немедленным откатом при FAIL и восстановлением TEST. Само по себе тихое окно или дополнительные свободные MiB не являются доказанным исправлением swap-in; без первого условия вариант не запускать.

Для любого нового окна и cutover нужно новое явное разрешение владельца. В данном задании ни TEST, ни production не останавливались и образ не загружался.
