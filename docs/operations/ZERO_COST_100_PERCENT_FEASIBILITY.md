# Можно ли завершить исходное ТЗ на нынешнем VPS без доплат

**Срез 16.10.2026, ответ: CONDITIONAL.** Дополнительная RAM/сервер/платный сервис не доказаны обязательными. Но текущие измерения **не подтверждают безопасный TEST API cutover или production Web release** на 2 GiB при работающем полном стеке. Даже если инфраструктурный путь пройдёт, буквальное требование исходного ТЗ к цели конверсии, которая «уже получает данные» (§§83–85), не может быть подтверждено serving metrics из одного Google TEST-аккаунта: [Google прямо указывает, что test accounts не показывают рекламу и их conversion/cost/impression metrics пусты](https://developers.google.com/google-ads/api/docs/best-practices/test-accounts). Нужен уже существующий и разрешённый реальный рекламный ресурс с настоящими данными либо отдельно согласованное сужение приёмки. Это **внешнее условие, не расходы на новый VPS**. Открытую фразу §4 «менять всё, что сейчас делается руками» нельзя честно превратить в конечный набор без согласованной границы типов кампаний и операций.

Никакой вариант не доказывает сегодня, что полный обязательный стек устойчиво проходит guard **после** нового TEST API и **после восстановления** ранее остановленных TEST-компонентов. Потенциальная экономия 56,5 MiB transient близка к наблюдённому нижнему дефициту 52,3 MiB, но этого математически недостаточно: события происходят в разные моменты, Web/production/host reclaim накладываются, PSS и MemAvailable не складываются линейно. Строго необходимый новый размер RAM нельзя вывести из этих рядов без профиля пиковой нагрузки; утверждать «2 GiB гарантированно достаточно» или «обязательно нужен 4 GiB VPS» было бы недоказанно.

## Условия для ответа «100% без доплат»

1. Согласовать конечную трактовку открытого §4 и настоящих неподдерживаемых source/component profiles. Требования, документированные Google как несовместимые с данным campaign type, учитываются как условные API boundaries; локальный unsupported profile не становится таким автоматически.
2. Без изменения guards показать **полный** preflight, один разрешённый cutover для TEST Web/API по отдельным approvals, затем post-start полный стек и production latency/health PASS; rollback готов. Новые образы должны соответствовать точному SHA, а TEST/production DB, vault, OAuth и rollback сохраняются.
3. В TEST получить реальные Google provider `validate_only` и отдельные owner/browser approvals для ConversionAction, PAUSED PMax fixture и каждого обратимого edit/restore. Current `WEBPAGE/SIGNUP` validate-only не является созданным action. Для аудитории и BRANDS нужен настоящий owned eligible resource; отсутствие его не означает API unsupported. [Официальный Google PMax критерий](https://developers.google.com/google-ads/api/performance-max/create-campaign-criteria) поддерживает negative keyword/brand exclusions; [asset requirements](https://developers.google.com/google-ads/api/performance-max/asset-requirements) требуют реальные тексты/изображения/логотипы и верный способ линковки при brand guidelines.
4. Для условия «цель получает данные» и performance-filtered примеров использовать уже имеющийся разрешённый **реальный** аккаунт/событие, если он доступен без новых расходов и без нарушения политики; либо явно принять, что эти пункты остаются внешне заблокированными. Google TEST не производит serving data.
5. Закрыть R/S существующими клиентскими артефактами или новым безопасным независимым разрешённым UX-тестом без повторения Google mutations ради снимков. Production release: отдельные security/rollback/access review и отдельное разрешение владельца; все production write flags пока OFF.

**Решение:** при существующем VPS путь **возможен только условно**, а capacity остаётся **не доказанной**. Если хотя бы полный post-start guard с обязательным TEST Web/API не проходит после проверенных бесплатных изменений, deployment остановить; тогда 100% на текущей конфигурации без изменения требования/ресурса **не подтверждается**. Если реальных conversion данных/Google ресурсов нет, даже идеальная инфраструктура не закроет буквальное исходное ТЗ. Следующий шаг — [единый план](../acceptance/FINAL_EXECUTION_PLAN.md), сначала offline blocker inventory, затем минимум отдельных resource-gated попыток и owner stop-points.
